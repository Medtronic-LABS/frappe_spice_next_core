Frappe for Spice

How the Frappe framework's app/site model lets one clinical core serve every country, and how a client running their own ERPNext gets connected to it — grounded in spice_next_core, the Frappe-side build of spice's clinical domain (Patient, Encounter, Observation, and the rest).

01 — Vocabulary

Framework, app, and site are three different things

Frappe is a metadata-driven web framework: define a DocType once and it generates the database table, REST API, desk UI, permissions, and print format together. Everything built on it — including the standalone product ERPNext — is packaged the same way: as an app. What's easy to conflate is the app and the site it runs on.

bench
One shared workspace on disk. Holds every installed app's source under apps/, shared by all sites on that machine.
app
A Python package: DocTypes, hooks.py, fixtures, client/server code. frappe itself is one; so is spice_next_core; so is ERPNext.
site
One tenant: one database, one site_config.json, and its own chosen subset of the bench's apps.
DocType
The unit of modeling — one JSON definition becomes a table, an API, a form, and a permission surface.

A bench built around spice's domain would typically hold four kinds of apps: the framework itself (frappe), the clinical core (spice_next_core), a reusable community theme app (frappe_theme), and any optional integration app a given deployment needs — e.g. a telephony integration such as shukhee_integration, which would declare required_apps = ["spice_next_core"]. ERPNext isn't part of this by default — it shows up later only where it's relevant as a general integration target.

Why frappe_theme, specifically

frappe_theme isn't ours — it's a community-built desk theme app (github.com/Suvaidyam/frappe_theme), pulled straight in via bench get-app frappe_theme --branch development https://github.com/Suvaidyam/frappe_theme.git and installed like any other app. Desk theming — layout density, color system, navigation chrome — is a solved problem elsewhere in the Frappe community; building a bespoke one would mean maintaining CSS/JS that has nothing to do with spice's clinical domain. This is section 03's "extend without forking" principle applied to UI: reuse someone else's app, keep customizing your own.

One thing this vocabulary doesn't decide on its own: whether many countries share one bench (Frappe's built-in multi-tenancy) or each gets a fully separate deployment. This platform uses the latter — see §04.

02 — Runtime

What's actually running underneath: cache, queue, database

Every mechanism above — hooks firing, jobs enqueuing, sites answering requests — sits on infrastructure every Frappe deployment needs to provision. The Redis instances and the database choice are worth being deliberate about before a client-facing rollout.

Cache — redis-cache

A single Redis instance backing frappe.cache(): hot metadata (DocType schema, permissions, translations, route maps) so a request doesn't re-read the database on every call. Invalidated automatically when a relevant doc is saved — app code almost never touches Redis directly.

frappe.cache().get_value("key") frappe.cache().set_value("key", val)
Queue & workers — redis-queue

Backs Frappe's background job system (RQ). bench worker processes pull from priority lanes (default / short / long). This is the exact mechanism behind enqueue_fhir_push in hooks.py and the connector's step 3 above; scheduler_events are the same queue, just triggered on a timer.

frappe.enqueue("app.module.fn", queue="short", **kwargs)
Realtime — redis-socketio

A third, separate Redis instance — pub/sub only, for the desk's live updates (form-level "someone else is viewing this," list auto-refresh). Not cache, not the job queue; don't conflate the three when reasoning about what a Redis outage takes down.

frappe.publish_realtime( "doc_update", doc.name)
Database — Postgres

Frappe's ORM targets one backend per site, fixed at site-creation time via bench new-site --db-type postgres --db-host postgres. Postgres is a fully supported backend alongside MariaDB — picking it deliberately, rather than defaulting to whichever comes first in a tutorial, keeps the platform on one database engine end-to-end when other services in the broader stack already run on it.

bench new-site ... \ --db-type postgres --db-host postgres
One thing to check before relying on it

The DB backend is a bench new-site–time decision, not something changed after data exists — so it's worth locking in before real data lands. Postgres support in Frappe is genuine but newer and less exercised by the wider ecosystem than the historically MariaDB-first default; each installed app (spice_next_core, frappe_theme, shukhee_integration) is worth a quick pass for any raw SQL written against MariaDB syntax before depending on it in production.

03 — Extensibility

Every lever below adds behavior to an app you don't own the source of

This is the mechanism that makes "integrate with ERPNext" or "customize per country" possible without forking anything. All of them appear in spice_next_core/hooks.py, or have a direct ERPNext-facing equivalent.

Custom Field / Property Setter

Add a field, or override a label / mandatory / hidden / permission-level property, on a DocType owned by another app — stored as data, no source edit.

fixtures: filtered "Property Setter" → the sva_ft FHIR-mapping channel
hooks.py — doc_events

Attach a handler to any DocType's lifecycle event, including one from another app.

"*": {"validate": "...validate_clinical_fields"} "Observation": {"after_insert": "...enqueue_fhir_push"}
override_doctype_class

Swap in your own Python controller for a DocType you didn't define — full behavioral override, schema and UI stay put.

override_doctype_class = { "Sales Order": "spice_core.overrides.SalesOrder"}
override_whitelisted_methods

Replace the implementation behind a whitelisted API path, e.g. one of ERPNext's, while callers keep calling the same dotted path.

override_whitelisted_methods = { "erpnext...make_delivery_note": "spice_core..."}
scheduler_events

Cron-style hooks, declared per app.

scheduler_events = {"hourly": ["spice_next_core.fhir.pull.do_pull"]}
required_apps

Declares install-order dependency between apps on the same site.

required_apps = ["spice_next_core"] — e.g. shukhee_integration
Server Script

Python attached to one DocType's server event, written and saved from the Desk UI itself — no app, no deploy. A country's own admin can add one without a developer touching hooks.py.

Server Script: "Referral" → "After Insert" notify receiving facility via Shukhee — no code push required
Client Script

JavaScript attached to a DocType's form, controlling what the user sees before anything is saved — show/hide a field, set a default, block submission on a bad value.

Client Script: "Household" form hide "Head of Household" until Household Type = "Registered"
Custom API

Not just overriding an existing whitelisted method — any app can define a brand-new Python function decorated with @frappe.whitelist() and get a live endpoint at /api/method/<dotted.path>, for business logic that isn't CRUD at all. This is the same mechanism behind spice_next_core's own sync.push/sync.pull and the connector's pull API (§06) — nothing about it is sync-specific; it's the general way to expose server-side computation to the Flutter app or any other caller.

@frappe.whitelist(methods=["GET"]) def household_risk_summary(household_id): # aggregates Observations + Encounters server-side, # shaped for the CHW worklist screen — # one call instead of the client stitching several return {...}
04 — Deployment shape

One core, many countries — separate deployments, shared code

Spice's domain, rebuilt as spice_next_core, is country-agnostic on purpose — but a country or client here is not a site sharing one bench with the others. It's its own deployment: its own bench, its own site, its own database, cache, and queue. Frappe's shared-bench multi-tenancy is a real capability (§01); this platform deliberately doesn't use it, trading density for isolation — one country's outage, upgrade, or data-residency requirement never touches another's.

What a country app is allowed to contain — every item below is additive, so nothing here ever touches core's source:

  • required_apps = ["spice_next_core"] — the same install-order dependency shukhee_integration declares.
  • Custom Fields / Property Setters for country-specific form fields, labels, or mandatory rules on core's Patient / Encounter.
  • Its own doc_events in its own hooks.py, running alongside — not instead of — core's validate_clinical_fields, enqueue_fhir_push, and friends.
  • Its own fixtures: a country's Geography Node tree, terminology Concept set, Priority Rules — the same fixture mechanism core already uses for its own reference data.
  • override_doctype_class, reserved for the rare case a country genuinely needs different controller behavior on a core DocType.
  • Optional apps aren't all-or-nothing either — shukhee_integration is installed into Bangladesh's deployment because Bangladesh needs telephony, and left out of Kenya's entirely, without either deployment's core or country app changing.
05 — ERPNext

Bringing ERPNext into the picture

ERPNext is, mechanically, just another Frappe app — same install-app command, same hooks.py levers from section 03 apply to it. There are two honest ways to bring it in, and they cost very different amounts.

PatternWhat it meansCost
A — Compose alongside Install ERPNext and a new domain app on the same site. They share one DB, one user/role/permission system, one desk shell, notifications, print formats, background jobs — for free. The domain app's DocTypes Link to ERPNext's rather than reimplementing them (e.g. a Household Visit DocType linking to ERPNext Healthcare's Patient). Low, if the domain genuinely overlaps with what ERPNext already models well.
B — Extend in place Don't add DocTypes — bend ERPNext's existing ones (Healthcare's Patient, Patient Encounter) with Custom Fields, Property Setters, doc_events, and override_doctype_class until they fit. High once the target invariants diverge from ERPNext's assumptions — see below.
Why spice_next_core picked neither

It built Patient, Encounter, and the rest from scratch. ERPNext Healthcare assumes server-assigned naming series (conflicts with client-mintable UUIDv7 IDs), mutable encounter records (conflicts with append-only clinical facts), and has no built-in FHIR egress or catchment-scoped row permissions. Retrofitting all four via Pattern B means overriding most of Healthcare's core behavior anyway — at which point Patterns A and B stop saving effort over building fresh.

Recommendation: reach for ERPNext when the need is genuinely ERP-shaped — inventory, procurement, accounting, HR/payroll for CHW supply chains — where none of those four invariants are in tension. Don't reach for it to model clinical facts; that's exactly the ground spice_next_core stakes out instead.

06 — Client-owned ERPNext

When a client already runs their own ERPNext

Different scenario: a country or client already operates ERPNext plus their own facility customizations, and needs data flowing to and from the Spice side. The answer isn't a fork of their ERPNext, or a rewrite of their customizations — it's a small, generic connector app installed on their site.

  • Trigger = doc_events, the same primitive from section 03: {"Patient": {"after_insert": "connector.sync.on_change"}}, added by the connector app — ERPNext's own code is never touched.
  • Push is queued, not inline — frappe.enqueue(...) means a slow or failing remote call never blocks the user's save. Mirrors how spice_next_core already runs enqueue_fhir_push from a hook rather than inline in validate.
  • Pull side is a whitelisted custom API, the same @frappe.whitelist(methods=["POST"]) pattern behind spice_next_core.api.sync.pull — so a remote system can ask on its own schedule instead of only receiving pushes.
  • Config-driven mapping, not hardcoded per client — a Connector Field Mapping DocType holding {source_doctype, source_field, target_field, transform} rows lets one connector codebase adapt to different clients' ERPNext customizations by adding rows, not code.
  • Auth — Frappe's built-in API Key/Secret on a dedicated Integration User, scoped by that user's role and permission_query_conditions if row-level scoping is needed. No bespoke auth layer.
  • Generic app, per-client companion only when logic (not just fields) diverges — same shape as section 04's core-plus-country-app split: connector_<client> with required_apps = ["connector"], reserved for genuinely bespoke transform logic.
